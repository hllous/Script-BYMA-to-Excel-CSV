## Post-preset-menu bug-fix round (done)

The user tried the preset-menu build for real (`run.bat`) and reported 6 issues. Diagnosed via `mattpocock-skills:diagnosing-bugs` (tight feedback loops built with the same fake-TTY `stdin`/`onRun` technique, driving the *real* production code, not reimplementations) before touching any code:

1. **Verbose inline instructions → short "key = action" footers**, applied to all three prompts (format `Select`, preset `MultiSelect`, per-ticker `AutoComplete`).
2. **No way to go back.** Added a `BACK_CHOICE` ("Volver al menu") row to the per-ticker picker, gated by a new `allowBack` option (only set when reached via the preset menu's "Custom", so standalone/direct callers are unaffected). `buildSymbolSelectionShape` gained a `backRequested` flag (same pattern as the existing `updateRequested`). `promptForInstrumentSelection` loops back into the preset menu when the picker reports `back: true`.
3. **"No" to reuse didn't unmark the old selection.** This directly reversed ticket 05's original spec wording ("pre-check as a starting point") — confirmed with the user before changing it: **"No" now discards the old selection entirely** and starts completely blank, same as a first-ever run. Simplified `promptForSymbolSelectionWithReuse` accordingly (removed the now-dead `initialSelection`/pre-check plumbing from `promptForInstrumentSelection` and `promptForInstrumentPresetMenu` entirely — nothing consumes it anymore).
4. **`"__custom__"` shown instead of `"Custom"` after confirming the preset menu.** Root cause (found by reading `node_modules/enquirer/lib/prompts/select.js`): `Select`/`MultiSelect`'s default `format()` echoes the raw `choice.name` (internal identifier) once submitted, not `choice.message` (the label) — `AutoComplete` already overrides this correctly, `MultiSelect` doesn't. Fixed by passing a `format()` override in the `MultiSelect` constructor options (enquirer's `setOptions()` binds function-valued options as instance methods, confirmed by reading `lib/prompt.js`). Every preset-menu label was already properly capitalized (`Todos`, `Acciones`, etc.) — that part of the complaint was actually already correct, just masked by the raw-name-echo bug.
5. **Stray "..." while typing in the per-ticker picker.** Root cause: `Select.prototype.separator()` deliberately renders a muted ellipsis in place of the normal pointer while the prompt is pending, unless a truthy `separator` option is passed. Fixed with `separator: "›"`.
6. **The big one — wrong symbol counts + unreadable timestamps.** Two independent root causes, both confirmed via reproduction scripts hitting the real `enquirer` prompt before any fix was attempted:
   - **A genuine bug in `enquirer` itself** (not application code): `ArrayPrompt.toggle()`'s parent-rollup walk (`lib/types/array.js`) computes a category header's `.enabled` from `parent.choices.filter(ch => this.isDisabled(ch))` — vacuously `true` whenever no child is literally flagged disabled, so it wrongly declares the header "fully enabled" after toggling just one child. A separate corrective pass (the free `reset()` function, also in `array.js`) normally fixes this — but only for headers still present in the prompt's *currently rendered* choices, which excludes the header entirely once a search filter narrows the view to matching leaf children (headers rarely match `message` text search). Net effect: search for a ticker, tick it, and its category header can get stuck reporting "fully selected" — exactly reproducing the user's "picked 4 individual tickers, got the whole 98-symbol `acciones` category" report. Confirmed via a battery of scripts (`repro-issue6*.js`) toggling with vs. without an active filter before finding the exact line. Fixed in **our own code**, not enquirer: `buildSymbolSelectionShape` no longer trusts a category header's own `.enabled` flag at all — it recomputes "fully selected" purely from whether every child's own `.enabled` is `true` (children's flags were never observed to be wrong, only the header rollup was).
   - **Unreadable raw ISO timestamps** in the live log/console (`2026-07-31T01:17:49.898Z`): `Logger.write()` used `new Date().toISOString()`. Extracted the existing `formatDateInArgentina()`/`getDateInArgentina()` helpers (previously private to `appRunner.js`, already used for the final stats block) into a new shared `src/utils/dateFormat.js`, and pointed `Logger` at `formatDateInArgentina()` too, so every log line now reads like `[30/07/2026, 10:43:02 p. m.]`.

Verified end-to-end with a real IOL login (this machine has real network access + the user's real saved credentials in `config.local.json`): picked 4 individual tickers across 4 different categories via search, and confirmed the aggregation log showed `Loading acciones: 1/1 (100%)` (not `98/98`) for every one of them, with readable timestamps. Full script: see conversation for `final-verification.js` (scratchpad, not committed).

`npm test`: **127/127 passing** (regression tests added for the enquirer quirk, the back-button flow, and the blank-on-decline behavior).

## Full business-logic audit + fixes (done)

Read through every service/util in the app (`authService`, `iolHttpClient`, `instrumentDiscoveryService`, `quoteAggregationService`, `exportService`, `symbolCacheService`, `lastSelectionService`, `credentialVaultService`, `asyncPool`, `quoteSchema`, `argParser`, `configLoader`) looking for behavior that's silently wrong, not just style. Found and fixed:

1. **`CredentialVaultService.getPassword()` could crash the whole app.** The real `@napi-rs/keyring` binding throws when no entry exists for a service+account (Rust `keyring-rs`'s `Err(NoEntry)` surfaces as a JS exception) - it does not return `null`/`undefined`. `deletePassword()` already had a try/catch for exactly this reason (see its existing comment); `getPassword()` didn't, so a fresh machine with a configured username but nothing yet saved to the vault would hard-crash on the very first run instead of falling through to the masked-password prompt. Fixed by wrapping it in try/catch, matching `deletePassword()`.
2. **Market-status close-time was silently wrong (real bug, real logic error).** `buildArgentinaTime()` called `getDateInArgentina()` a second time on a value that had already been through it - `getDateInArgentina()` works by taking a real `Date`, formatting it into an Argentina-wall-clock string, then re-parsing that string *as the host machine's own local timezone* (a trick that only works when applied exactly once: native `.getHours()`/`.getDay()` then read back Argentina's wall-clock numbers regardless of the host's real timezone). Applying it twice double-shifted the result by (host timezone offset − Argentina's fixed UTC-3 offset) - invisible only because every place this has ever run so far happened to already have its system clock set to Argentina time (offset difference = 0). Rewrote `buildArgentinaTime()` to derive the close instant directly via `Date.UTC(...) + 3h`, verified correct with a standalone script (`now: ...11:19pm` → `estimated close: ...05:00pm`, i.e. today 17:00 ART, independent of host timezone).
3. **Selection screens could be submitted completely empty**, which used to sail through the picker/menu only to blow up later with a generic, unfriendly "La seleccion de instrumentos no contiene opciones validas" crash deep inside the run - not at the moment of the actual mistake. Fixed with `validate()` on both the preset `MultiSelect` and the per-ticker `AutoComplete` (`src/interactiveMenu.js`): submitting with zero categories/tickers picked (and neither "Volver al menu" nor "Actualizar lista" requested) is now rejected in place, with an inline error, and the prompt stays open. Verified with fake-TTY scripts: pressing Enter with nothing picked now leaves `prompt.state.submitted === false`.
4. **No way back from the format screen.** Picking a preset/custom selection then reaching "Formato de salida" was a dead end - misclicking meant redoing the entire flow via "Volver al menu" from a screen that didn't even offer it. `promptForOutputFormat()` now takes `{ allowBack }` and adds a "Volver a seleccionar instrumentos" row (`BACK_CHOICE`); `appRunner.js`'s `main()` wraps instrument-selection + format-selection in an inner loop that redoes instrument selection (blank, no reuse prompt - see below) when the user backs out.

## Loop rerun behavior (done - explicit request)

Three changes to how "run the script again" behaves, all in `src/appRunner.js`'s `main()`:

1. **Home banner reprints on every restart** - `printHomeBanner()` moved from once-before-the-loop to the top of every `useInteractiveMenu` pass (both the outer post-run loop and the inner back-from-format loop).
